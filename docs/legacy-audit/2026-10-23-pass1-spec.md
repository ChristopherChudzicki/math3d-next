# Legacy audit, pass 1: rehydrated-vs-migrated comparison

**Status:** reviewed (methodology and feasibility), ready to plan · **Project:** `wp-verify-legacy-scene-migration-before-math3d-org--63f4d1`

## Short version

For every legacy scene, compare **what math3d-react shows** (the scene rehydrated by math3d-react's own `rehydrate`) against **what math3d-next receives** (the translator's output), property by property. The comparison uses an expected-translation table written from the two apps' runtime code, never from the translator. The output is a per-scene findings file (gitignored) and an aggregate report (committed), both counting raw scenes and scenes weighted by `LegacyScene.times_accessed`.

## Why rehydrate instead of inventorying blobs

math3d-react saves each item as a diff against its defaults. `dehydrateMathObjects` (`client/src/store/hydration.js`) keeps only properties that differ from `defaultSettings`, or from `initialState` for the camera, axes, grids and the three default folders. A property left at its default is absent from the blob. The translator reconstructs those defaults from its own Python copy (`legacy_data.py`, `default_data.py`, `default_items` in `migrate_scene.py`). A mistake in that copy is invisible both to an inventory of blobs and to a review of the translator alone.

Two such mistakes are already confirmed on the 2026-10-22 snapshot. Both come from defaults being merged at the item level instead of the property level:

- **Grids:** a `grid-yz` the user turned on is saved as `{type: GRID, visible: true}`, because `axes: 'yz'` matches `initialState` and is diffed away. The translator then sees no `axes` and falls back to `xy`. 11,071 of the 11,072 blobs that store `grid-yz` lack `axes`, and the same is true of 11,111 `grid-zx` blobs.
- **Folders:** default folders saved with partial settings lose their descriptions and become `"Folder"`: 6,381 `axes` folders and 20,451 `cameraFolder`s.

## Pipeline

```
math3d-next                         math3d-react                       math3d-next
export_legacy_audit ──legacy.jsonl──▶ rehydrate audit (Jest) ──rehydrated.jsonl──▶ audit_legacy_migration
 (key, times_accessed, dehydrated,    (rehydrated state, legacy-breakage        (zip both files line by line;
  migrated | migrate_error)            checks, same line order; defaults.json)    findings.jsonl + report.md)
```

All generated files go in the **main checkout's** `db-snapshots/legacy-audit/` (gitignored as prod-derived data), always as an absolute path. A relative path would land inside the worktree and be lost when the worktree is removed.

### 1. `export_legacy_audit` (math3d-next management command)

- Iterates over `LegacyScene` with `.iterator(chunk_size=…)` and writes to the database nowhere. It never calls `migrate_scene` or the scene GET endpoint, because both write.
- Runs the pure `translate_legacy_scene` (see "Translator refactor") on each scene, then `validate_math_items(items)`, so that `migrate_error` covers everything that makes GET return a 500. `Scene.save()`'s `full_clean()` re-validates items, and the pure function stops before that.
- Writes one line per scene: `{key, times_accessed, dehydrated, migrated: {items, item_order, title, creation_date} | null, migrate_error: {type, message} | null}`, ordered by `LegacyScene.id`.
- This is the shared input from the data contract (memory `ctx-legacy-scene-migration-audit-architecture-file-l-a9629a`); pass 2's evaluators read the same file.

### 2. Rehydrate audit (math3d-react)

- Lives at `client/src/legacyAudit/rehydrate.audit.js`. It must **not** be named `*.test.js` or `*.spec.js` or sit in `__tests__/`, because those match CRA's default `testMatch` and would join the normal suite. Run it with `CI=true npm test -- --watchAll=false --testMatch '<rootDir>/src/legacyAudit/**/*.audit.js'`. react-scripts 3.4 forwards the flag to Jest 24, which lets the CLI override the config (verified with a probe).
- Input and output are absolute paths from env vars. It streams with `readline` and `for await`, writes with `fs.writeSync` per line, sets an explicit test timeout, and never logs per scene. Output keeps the input's line order.
- For each scene, calls the real `rehydrate` from `store/hydration.js` and writes `{key, mathGraphics, mathSymbols, folders, sortableTree, sliderValues, metadata, legacy_broken: [reasons]}`.
- `legacy_broken` records failures that math3d-react hits at load or render time, not only in `rehydrate`, which is pure merging and rarely throws:
  - `rehydrate` throws;
  - the folder selector `getItems` throws for any folder (a tree id with no item);
  - a slider whose `value === null` has no entry in `sliderValues`.
- Also writes `defaults.json` once: `defaultSettings` per type plus `initialState`. This file is code-derived, not user data, and is checked in as a test fixture.
- Constraints: math3d-react's CLAUDE.md allows no dependency changes; the project memory adds that everything lives in one deletable directory. Verified 2026-10-23: `npm ci` plus the existing 21 suites pass under Node 24, and a probe importing `store/hydration` loads all 16 item types under jsdom with no errors.

### 3. `audit_legacy_migration` (math3d-next management command)

Zips the two files line by line and asserts that the keys agree. Then it produces the layers below and a per-scene verdict.

**a. Crash census.** Scenes with `migrate_error`, meaning a 500 in math3d-next. Grouped by exception type plus a message template with literals stripped.

**b. Comparison.** For each rehydrated item, the expected-translation table produces an expected math3d-next value for each target field, which is compared with the migrated item. Each comparison gets one of these outcomes:

| Outcome            | Meaning                                                                                                                                                                                                                                                         |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `match`            | Equal                                                                                                                                                                                                                                                           |
| `match_normalized` | Equal after the tested normalizations: LaTeX whitespace (`\ ` and spaces), numeric tolerance for floats (camera vectors are emitted as Python `str(list)`), and number-vs-string where old blobs store `1` for `"1"`. Each normalization is reported separately |
| `mismatch`         | Different. **This is the finding**                                                                                                                                                                                                                              |
| `needs_eval`       | Cannot be settled without evaluating math, e.g. an axis `scale` of `2\pi` feeding the camera. Deferred to pass 2/3; counted neither clean nor unclean                                                                                                           |
| `dropped_expected` | A math3d-react property with no math3d-next counterpart, and a table entry that says why (e.g. `isDropDisabled`)                                                                                                                                                |
| `unknown_property` | A property that isn't in math3d-react's metadata for its type. math3d-react ignores it; it matters only if the translator crashes on it                                                                                                                         |

Item-level checks: every rehydrated item id exists in the migrated items with the same type, and vice versa. Order checks: each folder's children and the root order match (math3d-react's `root` is math3d-next's `main`). Scene-level fields: title (newlines collapsed; `Untitled` becomes empty) and creation date.

Pre-registered hypotheses that the report confirms or refutes, with counts:

- the `grid-yz`/`grid-zx` `axes` loss;
- the default-folder description loss;
- **axis scales are ignored:** `get_axis_scales` reads `item["properties"]["scale"]`, but legacy items are flat, so every scene gets scales (1, 1, ½) and custom-scale scenes get a wrong camera;
- **a 0 coordinate in the camera position becomes the default**, because the translator uses `x or default`;
- **an untouched camera is missing:** an untouched camera diffs to `{type}` and is dropped from the blob, and `default_items` has no camera;
- **slider value rule:** math3d-react uses `sliderValues` when `value === null`; the translator uses it when `value` is absent.

**c. Inventory.** Counts of each `(type, property)` that is present in the dehydrated blob, i.e. set to something other than its default. These are the denominators that give mismatch counts meaning.

**d. Defaults cross-check.** A static comparison, run once, of `defaults.json` against the translator's Python copies (`legacy_data.py`, `default_items`, `DEFAULT_FOLDERS`). Used to explain clusters in (b); not counted again.

### Expected-translation table

`webserver/scenes/legacy_audit/expected.py` covers every math3d-react type. For each property it gives either a target field plus a transform, or `dropped("reason")`. Properties that depend on each other get an item-level transform: `CAMERA` (`useComputed` selects computed vs relative; relative coordinates relate to axis scales through each app's coordinate system), `VARIABLE_SLIDER` (value from the manual `value` or `sliderValues`), and the surfaces' domains. Constants that exist only in math3d-next (`zOrder`, `fps`, `duration`, `updateOnDrag`, an axis's `start`/`end`/`divisions`, a grid's `width`/`snap`) are expected to take whatever value reproduces math3d-react's _rendering_, cited from math3d-react's code. That is not necessarily math3d-next's default, and not the translator's constant.

**Independence rules.** The table only means something if it is written independently of the translator:

- It is written by an agent that is forbidden from reading `webserver/scenes/legacy_scene_utils/`. The agent works from math3d-react's metadata, hydration and rendering code and from math3d-next's `scenes/schemas/math_items.py`, `packages/mathitem-configs` and viewport code.
- Every non-identity transform cites the math3d-react code it reproduces and the math3d-next code that consumes the result.
- The table is committed before the first full run. Any later edit cites app code, never translator output.
- Every entry carries a pre-registered **severity**: `render` (changes what is drawn or computed), `editor` (visible only in the editor UI, e.g. `description`, `isCollapsed`), or `none`.

**Teeth.** Two tests check that the table actually catches things:

- Completeness: every property in the `defaults.json` fixture has an entry, and every target field exists on the math3d-next Pydantic model.
- Mutation: about five known bugs injected into the translator, e.g. swapping `rangeU`/`rangeV`, ignoring `scale`, flipping a bool, or dropping a property. Each must produce a `mismatch`.

### Metrics and report

**Weighting.** Use `LegacyScene.times_accessed` (incremented on both legacy and current GETs), never `Scene.times_accessed`. It is a lifetime count: biased toward old scenes and including crawler traffic. To keep that honest, the report also shows:

- the share of weight held by the top 1, 10 and 100 scenes;
- a `times_accessed + 1` variant, so zero-count scenes still count;
- a calibration set: the top 20 scenes by weight, each verdict checked by hand and listed by rank only.

**Headline.** The _pass-1-clean_ share, raw and weighted:

- A scene is clean when it has no crash, no item or order failure, and no `render`-severity `mismatch`.
- Scenes with `legacy_broken` are excluded from the denominator and reported separately.
- A stricter variant also counts `editor`-severity mismatches.
- It is labelled pass 1, because the ≥95% goal is a scene passing all three passes. `findings.jsonl` keeps a per-scene verdict that pass 2 can join.

**Root causes over symptoms.** A single wrong default mismatches nearly every scene, so findings are clustered by `(type, property, whether the legacy value is the default)`. The report includes a "clean if clusters 1..k were fixed" curve, which sets the fix order.

**Flags for pass 3.** Each scene in `findings.jsonl` carries flags so pass 3 can oversample the cases pass 1 can't settle: non-default axis scale, `useComputed`, `isOrthographic`, `needs_eval`.

**The committed report.** `docs/legacy-audit/reports/<date>-pass1.md`, aggregates only, because keys are access tokens to unlisted scenes. It contains:

- the snapshot date, counts, and the SHAs of both repos, including the math3d-react commit that is actually deployed;
- the headline variants and the weight-concentration figures;
- the crash census;
- clusters ranked by weighted impact, each with its inventory denominator and example value pairs that show only math3d-react defaults or other constants, never user values;
- each pre-registered hypothesis, confirmed or refuted;
- the defaults cross-check;
- `unknown_property` counts;
- the calibration result.

## Translator refactor (in scope)

Split `migrate_scene` into a pure `translate_legacy_scene(dehydrated: dict) -> TranslatedScene` (`items`, `item_order`, `title`, `creation_date`, `issues`) and the existing persistence wrapper. `set_defaults` gains a variant that takes a dict. The pure function deep-copies its input; today the in-place mutation is never persisted or read afterwards (`api.py` saves the legacy scene before migrating, and the final save uses `update_fields=["migration_note"]`), so the copy is safe. The existing tests must still pass. The comment at `api_test.py:357` that describes in-place mutation is updated. **The refactor fixes none of the bugs above.** Translator behavior is unchanged; fixes are separate tasks.

## Running from the worktree

`docker compose run` executes the main checkout's code, so run the worktree's code on the host from `webserver/`:

```bash
IS_DEPLOYMENT=False DATABASE_URL=postgresql://docker:docker@localhost:5431/math3d uv run python manage.py <command> # pragma: allowlist secret
```

`EnvConfig` reads no `.env`, so without `IS_DEPLOYMENT=False`, settings demand deployment configuration. Make sure no `DJANGO_SETTINGS_MODULE` is exported from another checkout.

## Out of scope

- Fixing the bugs this finds. Each confirmed cluster becomes a task under the epic.
- Expression evaluation (pass 2) and rendering (pass 3).
- `migration_note` severity and per-scene error handling in `migrate_legacy_data` (a separate task).

## As built

Where the tooling ended up differing from this spec:

- No property inventory: the report's denominators are scene and comparison counts.
- Normalizations also include `index_shift`, math3d-next's 0-based array indices. It reuses the translator's shift, which `packages/legacy-audit/` checks against math3d-next's parser.
- A **verified clean** headline row excludes scenes with a `needs_eval` or `expectation_error` comparison.
- `manual_checks.json` lists the most-viewed scenes a policy changes, for a check by hand.
- Fixing the translator bugs this found was in scope after all; see the [report](reports/2026-10-23-pass1.md).
