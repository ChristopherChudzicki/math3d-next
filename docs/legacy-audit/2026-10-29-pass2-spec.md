# Legacy audit, pass 2: evaluation comparison

**Status:** draft, reviewed once · **Project:** `wp-verify-legacy-scene-migration-before-math3d-org--63f4d1`

## Short version

For every legacy scene, evaluate each math field **in math3d-react** (the rehydrated scene, through its own parser and scope) and **in math3d-next** (the migrated scene, through MathScope and the item validators). Each evaluator reduces every value to a JSON fingerprint, sampling functions at shared points. A join pairs the two apps' fields and labels each pair. Pass 1 showed that the translation copies the right text; pass 2 checks that the text means the same thing in both apps.

## Pipeline

```
export_legacy_audit ─ legacy.jsonl ──────────────────────────▶ 2a evaluateNext (Vitest) ─ eval_next.jsonl ──┐
rehydrate.audit.js ── rehydrated.jsonl ─▶ 2b evaluate.audit.js (Jest) ─ eval_react.jsonl ──────────────────┤
                                                                                                          ▼
                    legacy.jsonl, rehydrated.jsonl, pass1/findings.jsonl ───────▶ 2c audit_legacy_evaluation
                                                                                   → pass2/findings.jsonl, report.md
```

- Generated files are production data and go in the main checkout's `db-snapshots/legacy-audit/`, as in pass 1. The committed fixtures (`sample_points.json`, `fingerprint_cases.json`, hand-built scenes) are not.
- Every file is in `LegacyScene.id` order. 2c zips them line by line and asserts that the keys agree.
- 2b runs once per snapshot. The fix loop is: translator fix → `export_legacy_audit` → 2a → 2c.

## Evaluator output

Each evaluator writes one line per input line:

```
{version: 2, key, crashed: null | message,
 items: {<itemId>: {<field>: {status, message?, value?, deps, features}}}}
```

- `field` is the app's own property name: for math3d-react, a graphic's `computedProps` name, a symbol's `value`, or a slider's `min`/`max`; for math3d-next, a property with a math widget. A field holding an array (`domain`, `range`) is one field.
- `status` is `ok`, `parse`, `eval` or `validate`. An array field also carries `elements: [{status, message?}]`, because math3d-next fails an array as a whole (`AggregateError`). An element with no error of its own is `ok` but has no value when its array failed.
- `value` is the fingerprint (below), present only when `status` is `ok`.
- `deps`: the ids of the fields this one depends on, from the app's own dependency graph.
- `features` (2a only): the mathjs function names and syntax node kinds (index, range, conditional, relational, function assignment) in the field's expression.
- `message` is the error's message. Messages of nested errors are flattened (`AggregateError.errors`, the `lhs`/`rhs` of `DetailedAssignmentError`).
- One evaluator crashing on a scene writes `crashed` for that scene and continues, so there is always one output line per input line.

### 2a: math3d-next evaluator

- Location: `packages/legacy-audit/src/evaluateNext.spec.ts`. It's a Vitest file that is skipped unless `LEGACY_EVAL_NEXT_IN` (`legacy.jsonl`) and `LEGACY_EVAL_NEXT_OUT` are set.
- I/O: it streams with `readline` and writes with `fs.writeSync`, like `rehydrate.audit.js`; `legacy.jsonl` is more than 1 GB, too large to read as one string. It sets an explicit timeout and logs progress to stderr every 1,000 scenes.
- Input: `migrated` from `legacy.jsonl`. A scene with `migrate_error` is written as `crashed`.
- How it evaluates:
  - It copies `makeMathScope` (`app/src/store/scene/evaluation/mathScopeInstance.ts`) and `getIdentifiedExpressions` (`syncMathScope.ts`), about 40 lines with a pointer to the originals.
  - It de-duplicates items by id, as the app's `keyBy` does (`scene.slice.ts`).
  - It reads `results`, `errors` and the dependency graph per id.
- Stage tagging: the copy wraps `parse` and each property's `validate` so that their errors are tagged with their stage. `evaluate.ts` re-wraps validator errors as plain `EvaluationError`s, so the wrapper rethrows an `EvaluationError` subclass. The validate wrapper forwards the second `node` argument, which `domain2` uses.
- A surface `domain` validates to `{value: [f1, f2], order}`. Its fingerprint is `value`; `order` isn't compared, since pass 1 checked the swap.
- During the run, `Math.random` is a seeded PRNG, because `realFunc` samples at random points while validating. `console.warn` is stubbed, because `evaluate.ts` warns on every mathjs error.
- New dependencies: `@math3d/mathitem-configs`, `@math3d/mathscope`, `lodash-es`.

### 2b: math3d-react evaluator

- Location: `client/src/legacyAudit/evaluate.audit.js` on `legacy-audit/rehydrate`, run like `rehydrate.audit.js`. Its env vars are absolute paths: `LEGACY_EVAL_IN` (`rehydrated.jsonl`), `LEGACY_EVAL_OUT`, `LEGACY_SAMPLE_POINTS` and `LEGACY_FINGERPRINT_CASES`.
- A line where rehydrate failed (`{key, legacy_broken}` only) becomes `crashed`.
- It re-implements `MathBoxScene.render`'s evaluation and never imports `MathBoxScene.js`, `getCameraData` or `ScrollWithOverflow`: `MathBoxScene.js` builds a MathBox at module load. Safe imports are `containers/MathObjects`, `utils/mathParsing`, `services/evalData` and `containers/MathScopeContext/selectors`.
- **Per scene, a fresh `new Parser()` and the module function `evalScope`.** The shared `parser` and `scopeEvaluator` cache across scenes: expressions, mutated dependency sets, and the incremental scope patch.
- What it evaluates, matching a page load:
  - Symbols, all of `mathSymbols` (orphans included), through `getParseableSymbols` and `evalScope`. A symbol's `value` is its scope entry. Errors are keyed by name and mapped to ids through `idsByName`.
  - Every graphic's `computedProps` (the metadata keys with `inputType: 'math'`), through `evalData`. A non-string setting (a numeric `opacity`) is what MathBox receives, so its fingerprint is its literal value with status `ok`.
  - Each slider's `min` and `max`, through `evalData`, as `EvaluatedSlider` does. A non-number result, or `min ≥ max`, gets status `validate`.
- Symbols `getParseableSymbols` drops silently get a status:
  - an unparseable symbol, self-reference included, is `parse`;
  - each copy of a duplicate name is `eval`, with a message saying so.
- A graphic function with a missing dependency is `ok` in math3d-react, but throws at every point. See "No evidence" below.
- `deps`: a `MathExpression`'s `dependencies`, mapped through `idsByName`.
- Needs `npm ci` in `math3d-react/client` first.

### Fingerprints

| Value                                                        | Fingerprint                                           |
| ------------------------------------------------------------ | ----------------------------------------------------- |
| finite real                                                  | the number                                            |
| `NaN`, `±Infinity`                                           | `{"nonfinite": "NaN" \| "Infinity" \| "-Infinity"}`   |
| complex                                                      | `{"re": a, "im": b}`                                  |
| boolean, string                                              | `{"bool": b}`, `{"str": s}`                           |
| `undefined`                                                  | `{"undefined": true}`                                 |
| array or mathjs `Matrix` (any depth)                         | array of fingerprints                                 |
| function                                                     | `{"fn": arity, "at": [fingerprint per sample point]}` |
| function past the depth limit, or of an arity with no points | `{"fn": arity, "at": null}`                           |
| a sample point that throws                                   | `{"error": true}`                                     |
| anything else                                                | `{"other": type name}`                                |

- **Sample points:** `packages/legacy-audit/sample_points.json`, generated once and committed. For each arity 0–5 there are 16 points in (−3, 3)ⁿ: integer and structured points (0, ±1, ±2, mixed tuples) first, then uniform points. Arity 0 is one empty point.
- **Vector arguments:** when every scalar point errors, an evaluator also records `vec: {2: [...], 3: [...]}`: the same points with vector arguments of length 2 and 3 taken from the same file (`f(P) = P[1]·P[2]`). 2c uses `vec` when both sides have it.
- **Arity** is the function's `.length`. That is reliable for user functions and `diff(f)` in both apps. Builtins assigned to a symbol report their widest signature (`sin.length` is 2), so an arity mismatch is `unsure`, not `differ`.
- **Depth:** a function's outputs that are themselves functions are sampled at the first 4 points; depth is limited to 2.
- **Conformance:** both implementations pass `packages/legacy-audit/fingerprint_cases.json`, which lists expressions both parsers accept with their expected fingerprints. 2b's check is `client/src/legacyAudit/fingerprint.audit.js`, run by hand.

## Pairing

2c pairs fields using pass 1's table (`webserver/scenes/legacy_audit/expected.py`), re-run on each rehydrated item. That table already knows which legacy source feeds each math3d-next path, including the surface samples swap.

The rules, for each expectation:

- **next field:** the first segment of its `path`, kept only if 2a emitted that field.
- **legacy field:** the first token of its `source`, kept only if 2b emitted that field. Later tokens in the source are conditions (`relativePosition,useComputed`). The sources `sliderValues` and `value,sliderValues` map to legacy `value`.
- **element:** from `items.<i>` in the path (`domain`, `range`), or from the `samplesN` suffix (legacy `samples`, element N−1).
- A pair needs both fields. `NeedsEval` expectations are kept, since they are what pass 2 settles. Items with an `expectation_error` are skipped and counted.
- If either side's legacy text is blank, the pair is skipped: a blank is a pass-1 policy, not math.
- Pass 1's `severity` carries over to the pair.

Two shapes get their own rules:

- **Surface domains:** a legacy range that doesn't depend on the other parameter is an array; math3d-next's is always an arity-1 function. A legacy array equals a math3d-next function whose value at every point equals that array.
- **Cameras:**
  - 2c re-runs `expected._camera` with `Context` scales taken from 2b's evaluated `axis-x|y|z` `scale` (`?? 1` when a scale fails, as `useAxesInfo` does). That gives a numeric expected `position`/`target`: perspective and ortho are both handled (it undoes math3d-react's 50× dolly).
  - 2c compares that with 2a's evaluated `position`/`target`.
  - When `useComputed` is set, legacy `computedPosition`/`computedLookAt` are compared directly.
  - math3d-next's own ortho zoom (`ZOOM_FACTOR`) is rendering: pass 3.

**Completeness:** every field either evaluator emits is paired or appears in `KNOWN_UNPAIRED` (with a reason). If any field is unaccounted for, 2c exits non-zero. A table change that silently drops a pair would otherwise make every scene of a type look clean.

## Comparison

### Status

| Legacy | Next  | Outcome                                                                   |
| ------ | ----- | ------------------------------------------------------------------------- |
| ok     | ok    | compare fingerprints                                                      |
| ok     | error | `regression`, split by next stage                                         |
| error  | error | `both_error`: invalid source, not a finding                               |
| error  | ok    | `next_only_ok`: math3d-next is more lenient, or the translator rewrote it |

For an array field, the table applies per element.

**No evidence:** a function is treated as an `eval` error before the status table when, even after the vector retry, it has a finite value at no point. This covers a math3d-react graphic with a missing dependency, which is `ok` but throws everywhere.

### Values

Values are compared recursively:

- **Vectors:** a flat array of numbers (a point, a vector) is compared by norm: ‖a − b‖ ≤ atol + rtol·max(‖a‖, ‖b‖). A complex number is a 2-vector `(re, im)`, and a real is `(x, 0)`.
- **Nested arrays:** element-wise, then by the vector rule. Lengths must match.
- **Functions:** same arity, then point by point. Error and error at a point are equal; error and a value differ.
- **Other kinds:** nonfinite tags, booleans and strings must match exactly. Values of different kinds differ (`true` vs `1`).
- **Precedence:** within one pair, `differ` beats `unsure`, which beats `equal`.

Outcomes:

- `equal`: within atol/rtol.
- `differ`: anything else. A difference within the loose band (`--loose-rtol`) is tagged `loose`, but it is still `differ`. Both apps use the same derivative step, so real bugs sit in that band (see the first hypothesis).
- `unsure`, for one of a fixed list of causes:
  - `depth`;
  - `arity`;
  - `sparse`: fewer than half the points are finite on either side;
  - `other`: an `{"other": …}` fingerprint.

The flags are `--rtol 1e-6 --atol 1e-9 --loose-rtol 1e-3`. They are recorded in the report, which also has a histogram of the maximum relative error per compared pair, in decade bins. A gap in the histogram is the evidence that the cut-off is right.

## Findings and report

- **Roots.** A non-`equal` pair is a root when none of its transitive `deps` is non-`equal`; otherwise it is `downstream`. This applies to `differ`, `regression` and `both_error`. Clusters count roots only, so one `pdiff` symbol is one regression, not one per dependent.
- **Clusters.**
  - The key is `(type, field, outcome, signature)`. The signature is `loose`, `sign`, `scale` (a constant factor), `permuted`, `real_vs_complex`, `nan_vs_error`, `value_vs_error` or `other`.
  - Clusters are ranked by weighted impact, with a "clean if clusters 1..k were fixed" curve.
  - A feature-lift table shows, for each of 2a's `features`, its share among `differ` roots against its share among `equal` pairs.
- **Allowlist:** `legacy_audit/pass2_allowlist.py`. Each entry matches a `differ` or `regression` cluster and cites app code or an owner decision. A downstream pair inherits its root's entry. Allowlisted pairs are reported separately.
- **Scene verdict:**
  - _Pass-2-clean:_ no non-allowlisted root `regression` or `differ` at `render` severity. `both_error` and `next_only_ok` count as clean.
  - _Strict_ also counts `editor` severity.
  - _Verified clean_ also has no `unsure`.
  - A scene that crashed in 2b is excluded, like `legacy_broken`. A 2a crash is unclean, and pass 1's crash census already counts it.
  - The headline also shows clean through passes 1 and 2, joined with pass 1's `findings.jsonl`. All counts are raw and weighted by `LegacyScene.times_accessed`.
- **Committed report:** `docs/legacy-audit/reports/<date>-pass2.md`. It contains:

  - the snapshot date, both SHAs and the tolerances;
  - the headline variants;
  - clusters with value shapes and features;
  - each hypothesis, confirmed or refuted;
  - the calibration;
  - the error histogram.

  It holds aggregates only: error messages appear as templates with literals stripped, as in pass 1's crash census, so no user expression or key is committed. Example keys for filed tasks go in witan.

## Hypotheses to confirm or refute

Already seen in the code. Pass 2 counts each one.

**In math3d-next:**

- **`diff` bug:** `diff` never restores `copy[j]` (`custom-mathjs/src/derivatives.ts`), so for a function of several variables, ∂/∂y is evaluated at x + EPS/2. math3d-react restores it. Expect `differ`, tagged `loose` (`tk-math3d-next-diff-gives-wrong-partial-derivatives-86bc2b`).
- **Complex outputs:** `realFunc` wraps outputs in `Number(…)` (`validators.ts`), so a complex output of `expr` or `colorExpr` becomes `NaN`. Possibly intended, since NaN points aren't drawn; if so, it's an allowlist entry (`tk-math3d-next-realfunc-turns-a-complex-output-into-0f7f11`). Expect `differ` (`real_vs_complex`).
- **Negative imaginary parts:** `numericTypeSimplify` tests `val.im < 1e-10` without `Math.abs` (`parser/src/evaluate.ts`), so a negative imaginary part is dropped: `-\sqrt{-4}` gives `0`. Expect `differ` (`tk-math3d-next-a-negative-imaginary-part-is-dropped-e2db04`).
- **`diff(f)(x)`:** this is `diff(f)·x` (implicit multiplication). math3d-react rewrites it to `diff(f, x)` (`preprocessHOFs`). Expect `regression` (`tk-legacy-scenes-diff-f-x-is-diff-f-x-in-math3d-nex-eae136`).
- **Missing functions:** `pdiff` is undefined (`tk-legacy-scenes-support-math3d-react-s-pdiff-f-x-y-a84404`), and so is `flatten` (`tk-legacy-scenes-math3d-next-s-custom-mathjs-has-no-24dbe9`). Expect `regression`.
- **An array to a multi-parameter function:** `f(P)`, where `P` is a symbol or a function result, is "Too few arguments". math3d-react spreads it (`MathExpression.js`), but not for an inline `[1,2]`, which is a `Matrix`. Expect `regression`.
- **Open range:** `a[:]` skips the first entry (`tk-math3d-next-an-open-range-start-in-an-index-skip-7ee951`). Expect `differ`.

**In math3d-react:**

- **Missing operators:** its mathjs namespace has no relational or logical functions, no `!` or `factorial`, and no `random` (`utils/mathjs/custom.js`). So `T>0` and `n!` are parse errors there. Expect `next_only_ok`.
- **Different meanings:** `i`, `j`, `k` are unit vectors; `|` is `dot` and `&` is `cross`; `arctan(a, b)` is `atan2`; `curl`, `div` and `LegendreP` exist. Each is a candidate for `differ` or `regression`.
- **Orphans:** math3d-react evaluates items missing from the tree. If the translator drops them, their dependents show as `regression`.

**Both apps:**

- **Duplicate names:** math3d-react drops every copy; math3d-next reports "assigned multiple times". Expect `both_error`.

Confirmed math3d-next bugs are filed as tasks under the epic.

## Self-checks

- **Null test:** every fingerprint in a real `eval_next.jsonl` compared with itself is `equal`.
- **Conformance:** both fingerprint implementations pass `fingerprint_cases.json`.
- **Unit tests:**
  - each comparison and status rule on hand-built pairs;
  - pairing for each shape;
  - the completeness check.
- **End-to-end mutants:** on hand-built scenes, run 2a once as written and once with these mutations, against a committed 2b output for the same scenes, and assert each mutant is not `equal`:
  - the index shift skipped inside a function body;
  - swapped parameters `f(u,v) → f(v,u)`;
  - a sign flip in a symbol.
- **Calibration, by hand in both apps:**
  - the examples of the top 3 `differ` clusters;
  - 10 weighted-random `equal` scenes that use functions, which measures recall, not just precision.

## Blind spots

These are reported, not tested:

- Points outside (−3, 3)ⁿ: piecewise or `mod`/`floor` differences outside the box. A graphic is plotted over its own domain.
- Slider conditions at values other than the saved one (`T > 5 ? A : B` with `T` animated).
- Rendering: pass 3. That covers math3d-react's render-time checks, how the viewport maps explicit and polar surfaces, and how it evaluates domains.
